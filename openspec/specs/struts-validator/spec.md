# struts-validator Specification

## Purpose

Declarative commons-validator form validation: rules declared in `validation.xml` on top of `validator-rules.xml`, wired declaratively by `ValidatorPlugIn` through struts-config.xml, errors enter the standard Struts cycle (input page, `html:errors`), client scripts are generated by `html:javascript` — with the behavior of the weblegacy reference.

## Requirements

### Requirement: Wiring the validator as a plugin
`ValidatorPlugIn` SHALL be wired declaratively with a `<plug-in>` element of struts-config.xml with the init parameters `pathnames` (comma-separated list of resources: validator-rules.xml and validation.xml) and `stopOnFirstError`. Resources SHALL be loaded at startup; a repeated declaration of the plugin in a module SHALL be a startup error.

#### Scenario: Declarative wiring
- **WHEN** struts-config.xml declares `ValidatorPlugIn` with `pathnames` pointing to validator-rules.xml and validation.xml
- **THEN** the validator is initialized at startup, and forms are validated by the rules without additional code

#### Scenario: Missing pathnames resource
- **WHEN** `pathnames` points to a non-existent resource
- **THEN** application startup fails with an error naming the resource

### Requirement: ValidatorForm validation by rules
A `ValidatorForm` form (and its subclasses) SHALL be validated by the rules of validation.xml for its key name: the key is the form's attribute from the configuration (`mapping.getAttribute()`); detected violations SHALL return `ActionErrors` with rule messages, which the standard cycle directs to the input page; when there are no violations, the action is invoked.

#### Scenario: Required field left empty
- **WHEN** a field is declared `depends="required"` and submitted empty, and the mapping uses `validate="true"` with an input page
- **THEN** the action is not invoked, and the input page renders `html:errors` with the `errors.required` key message and the field label from `<arg>`

#### Scenario: Successful validation
- **WHEN** all fields of the form satisfy the rules
- **THEN** validate returns without errors and the action is invoked

### Requirement: FieldChecks rule set
The rule set of the reference `validator-rules.xml` SHALL work out of the box: required, requiredif, mask, minlength, maxlength, byte/short/integer/long/float/double (including the *Locale variants), date, intRange/longRange/floatRange/doubleRange, creditCard, email, url, validwhen. Messages SHALL be taken by rule keys (`errors.required`, `errors.invalid`, `errors.range`, etc.) from message-resources, arguments from the field's `<arg>` (positions 0–3, support for literals and `${var:...}`).

#### Scenario: mask rule
- **WHEN** a field is declared `depends="required,mask"` with `var-name="mask"`, and the value does not match the regular expression
- **THEN** the input page displays the `errors.invalid` key message with the configured `<msg>`/`<arg>` (including the bundle from the `bundle` attribute)

#### Scenario: Range rule
- **WHEN** a field is declared `depends="intRange"` with min/max variables, and the value is outside the range
- **THEN** the `errors.range` message is displayed with min/max substituted from `<arg>` with `${var:min}`/`${var:max}`

#### Scenario: validwhen rule
- **WHEN** a field is declared `depends="validwhen"` with a condition expression (`<var-name>test</var-name>`), and the condition is violated
- **THEN** the field is marked with the `errors.required` error

### Requirement: Multi-page validation with page
Fields of validation.xml with the `page` attribute SHALL be validated according to the form's `page` value: fields whose page is not greater than the current one are validated; when the mapping does not declare a page limit, all fields are validated. Forms `ValidatorActionForm`/`DynaValidatorActionForm` SHALL use the mapping path (`mapping.getPath()`) as the validation key.

#### Scenario: Second page of a multi-page form
- **WHEN** a multi-page form submits `page=2`, and the mapping limits the allowed pages
- **THEN** only fields with page ≤ 2 are validated; fields of page 3 are not validated

#### Scenario: Key by action
- **WHEN** the mapping uses a form of type `ValidatorActionForm`, and validation.xml declares rules by the action path name
- **THEN** validation is performed by that action's rules

### Requirement: DynaValidatorForm validation
`DynaValidatorForm` (a dynamic form extending `DynaActionForm`) SHALL be validated by the rules of validation.xml in the same way as a static `ValidatorForm`, without a Java form class; properties are taken from `<form-property>`, and the validation key is the form's attribute from the configuration.

#### Scenario: Dynamic form validated by rules
- **WHEN** struts-config.xml declares a form-bean of type `DynaValidatorForm`, validation.xml contains rules for its name, and the request submits invalid values
- **THEN** the rule errors are displayed on the input page, and the action is not invoked

#### Scenario: form-bean inheritance with validation
- **WHEN** a derived form-bean (`extends`) extends the base `DynaValidatorForm` with additional properties, and validation.xml declares rules under the derived name
- **THEN** both the inherited and the own properties are validated

### Requirement: Custom validators
Custom rules SHALL be wired via the `<global><validator>` section of validation.xml: rule name, class and method, message key; such rules SHALL be applied in `depends` on par with the built-in ones.

#### Scenario: Custom rule
- **WHEN** validation.xml declares a global validator `twofields` with a custom class, and a field declares `depends="twofields"`
- **THEN** the custom class's method is invoked, and on violation its key's message is displayed

### Requirement: Client scripts of html:javascript
The `html:javascript` tag SHALL generate commons-validator client scripts by the rules of validation.xml: static/dynamic mode, the form by `formName` (or the context form's attribute), field methods by their rules; the output matches the reference (form validation functions, `required` fields, rule JS utilities).

#### Scenario: Form script generation
- **WHEN** the JSP contains `<html:javascript formName="registrationForm"/>`, and validation.xml declares that form's rules
- **THEN** the page contains a JavaScript form validation function with checks for the declared rules

#### Scenario: StaticJavascript
- **WHEN** the JSP requests the static validator JS utilities (as in the mailreader StaticJavascript.jsp)
- **THEN** the commons-validator utilities script is served without binding to a specific form
