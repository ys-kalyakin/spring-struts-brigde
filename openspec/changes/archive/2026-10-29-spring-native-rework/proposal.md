# Proposal

## Why

Фазы 1–2 воспроизводят Struts 1 «как был»: Spring-бинами становятся только классы с аннотациями `@StrutsAction`/`@StrutsForm`, а остальные формы и экшены создаются через `newInstance` в обход Spring — без внедрения зависимостей и без жизненного цикла бина. Тэг-библиотеки — классические порты на статических синглтонах (`MessageResources.getMessageResources`, `TagUtils`) без доступа к Spring-контексту. Это копирование оригинала, а не интеграция: цель проекта — мост Struts 1 → Spring, поэтому движок должен быть Spring-нативным при сохранении классического API.

## What Changes

- **Все формы и экшены становятся Spring-бинами**: типы, объявленные в `struts-config.xml`, автоматически регистрируются в контексте как bean definitions при старте (экшены — singleton, формы — prototype). Явная регистрация пользователя (компонент-скан `@StrutsAction`/`@StrutsForm`, Java/XML-конфигурация) имеет приоритет над авто-регистрацией. Прямого создания через `newInstance` больше нет: любой экземпляр формы или экшена создаёт Spring (`AutowireCapableBeanFactory`). **BREAKING**: требование «фолбэк прямого создания» из `spring-bean-integration` заменяется авто-регистрацией — класс без аннотаций тоже становится Spring-бином.
- **Внедрение зависимостей работает в любой форме и любом экшене** независимо от аннотаций: `@Autowired`/setter-инъекция, колбэки жизненного цикла (`@PostConstruct`/`@PreDestroy`, `BeanPostProcessor`) применяются ко всем экземплярам. Классическая семантика жизни сохраняется: один экземпляр экшена на класс между запросами, свежая форма на каждый запрос.
- **Тэг-библиотеки переезжают на Spring-нативную реализацию**: Spring-aware база тегов даёт обработчику доступ к `WebApplicationContext`, общая логика тегов (резолв сообщений, построение URL, поиск формы в области, рендер ошибок) выносится в Spring-компоненты, тегам доступно внедрение зависимостей. Классический внешний контракт сохраняется: те же TLD/URI/имена/атрибуты тегов и тот же HTML-вывод (спеки `bean-taglib`, `html-taglib`, `logic-taglib`, `nested-taglib` остаются в силе), существующие JSP не переписываются.
- **MessageResources мостится на Spring `MessageSource`**: бандлы из `<message-resources>` регистрируются как `MessageSource`-бины; классический API `MessageResources` сохраняется поверх моста. Поведение без изменений: локаль из сессии, формат `???ru_RU.key???` (спека `message-resources` остаётся в силе).
- **Сосуществование в JSP**: на одной странице работают Struts-теги, теги Spring (`spring:message`, `spring:eval` и др.) и EL-доступ к Spring-бинам — «спринговый JSP-стек» поверх того же контекста.

Допущение (трактовка запроса): «спринговый движок JSP» понимается как JSP-стек Spring — инфраструктура тегов Spring (`RequestContext`, `MessageSource`, `spring:*`-теги, EL-доступ к бинам) — с которой Struts-теги интегрируются и построены на той же модели (Spring-aware теги + Spring-компоненты логики). TLD/URI/имена тегов и HTML-вывод не меняются.

## Capabilities

### New Capabilities

- `spring-tag-integration`: Spring-нативная инфраструктура тэг-библиотек — база тегов с доступом к Spring-контексту, логика тегов как Spring-компоненты (сообщения, URL, поиск формы), внедрение зависимостей в теги, мост `MessageResources` → `MessageSource`, сосуществование Struts- и Spring-тегов в одном JSP.

### Modified Capabilities

- `spring-bean-integration`: вместо «аннотированные классы — бины, остальные — прямое создание» — все формы и экшены являются Spring-бинами: авто-регистрация типов из `struts-config.xml` (приоритет у явной регистрации), создание любого экземпляра через Spring, внедрение зависимостей и жизненный цикл для всех.

## Impact

- **Код:** `spring-struts1-core` — `StrutsInstanceResolver` (создание через `AutowireCapableBeanFactory`), новый регистратор bean definitions из `ModuleConfig`, `StrutsEngineConfiguration`; `spring-struts1-taglib` — базовые классы тегов и общие помощники (`TagUtils`, резолв сообщений); `spring-struts1-apps` — демонстрация инъекции в примерах.
- **API:** классический API Struts 1 сохраняется (`Action`, `ActionForm`, сигнатуры `execute`/`validate`, TLD, URI, имена и атрибуты тегов); HTML-вывод тегов не меняется. **BREAKING** только в смысле жизненного цикла: класс без Spring-регистрации теперь проходит через Spring (получает пост-обработку бина).
- **Тесты:** существующие IT (`examples`, `blank`) проходят без изменений результатов — регресс совместимости; новые тесты авто-регистрации, инъекции в формы/экшены/теги, смешивания Struts- и Spring-тегов.
- **Зависимости:** новых нет (Spring context/web, jakarta servlet/jsp уже подключены).
- **Не входит в объём:** замена JSP другой view-технологией, struts-el, commons-validator, Tiles, изменение TLD/URI/имён тегов, смена HTML-вывода.
