# Design

## Context

Populate — единственный участок пути обработки запроса, зависящий от статического глобального реестра `ConvertUtils` commons-beanutils: `RequestUtils.populate()` собирает параметры в `Map<String, Object>` и отдаёт их `BeanUtils.populate()` (RequestUtils.java:235); для multipart-рационализации используется `PropertyUtils.getPropertyType` (RequestUtils.java:263). Остальные использования beanutils не входят в populate-путь и не меняются:

- **публичный API**: `DynaBean`-иерархия (`DynaActionForm`, `DynaValidatorForm`, `LazyValidatorForm`, `BeanValidatorForm`, `DynaActionFormClass`) — классы обязаны реализовывать интерфейсы beanutils;
- **валидатор**: `FieldChecks` (`PropertyUtils.getProperty`), `BeanValidatorForm` (`ConvertUtils.convert` для индекса);
- **конфигурация**: клонирование/копирование конфигов (`ActionConfig`, `FormBeanConfig`, `ActionServlet`, `ActionConfigMatcher`), начальные значения (`FormPropertyConfig`).

Поведение populate закреплено: IT всех тестовых приложений — `TestBean` в `examples` покрывает примитивы, массивы (`int[]`, `String[]`), индексированные (`intIndexed[0]`), вложенные (`nested`) и multibox; динамические формы в `cookbook`/`mailreader` — `String`, `Boolean`, `String[]`; multipart — `UploadForm`.

## Goals / Non-Goals

**Goals**
- Убрать статический реестр `ConvertUtils` из populate-пути: конвертация — через собственный `ConversionService` на базе Spring, с воспроизведением наблюдаемого поведения beanutils.
- Один сервис конвертации для обоих путей присвоения (JavaBean и DynaBean).

**Non-Goals**
- Убирать зависимость commons-beanutils из проекта (публичный API остаётся).
- Замена beanutils в валидаторе, конфигурации, клонировании конфигов.
- Точка расширения для пользовательских конвертеров приложений (кандидат отдельного изменения, если понадобится по итогам миграции).
- Любые новые возможности конвертации (например, `java.util.Date` не получает конвертер — так сегодня).

## Decisions

### 1. Собственный `StrutsConversionService` поверх Spring `ConversionService`

Новый класс `org.apache.struts.util.StrutsConversionService` — сервис на `GenericConversionService` с явным набором конвертеров, воспроизводящих дефолтный реестр commons-beanutils (поведение зафиксировано probe-замерами на beanutils 1.11):

| Целевой тип | Валидный ввод | Некорректный/пустой ввод |
|---|---|---|
| `Boolean`/`boolean` | литералы `true`,`yes`,`y`,`on`,`1` / `false`,`no`,`n`,`off`,`0` без учёта регистра | `false` (нулевое значение), без ошибки |
| `Byte`,`Short`,`Integer`,`Long`,`Float`,`Double` (+ примитивы) | триммируется, десятичный парсинг (hex `0x…` не поддерживается) | нулевое значение типа (0, 0.0), без ошибки, включая переполнение |
| `Character`/`char` | первый символ строки | пробел `' '`, без ошибки |
| `BigDecimal`, `BigInteger` | парсинг | ошибка populate |
| `String` | без преобразования (из не-строковых источников — `toString`) | как есть |
| `java.sql.Date`/`Time`/`Timestamp` | JDBC-форматы (`yyyy-MM-dd`, `HH:mm:ss`, `yyyy-MM-dd HH:mm:ss`) | ошибка populate |
| `Class` | загрузка класса по имени | ошибка populate |
| `File`, `URL` | путь / URL | ошибка populate (`URL`) |
| `Enum`, `java.util.Date`, `Calendar`, коллекции (`List`) | — конвертера НЕТ — всегда ошибка populate (совместимо с дефолтным реестром) | |

Массивы/коллекции: целевой массив заполняется покомпонентно (некорректный элемент — нулевое значение компонента), скалярная цель получает первый элемент массива параметров — стандартные `ObjectToArrayConverter`/`ArrayToObjectConverter` Spring с конвертацией элементов через тот же сервис. `FormFile` присваивается без конвертации при совпадении типов.

**Альтернативы**: чистый `DefaultConversionService` — отклонено (иные литералы Boolean без `y`/`n`, ошибки вместо нулевых значений для чисел, поддержка hex и enum, которых нет в реестре beanutils); оставить beanutils с изоляцией на уровень запроса — отклонено (не устраняет статический реестр и не интегрируется с Spring).

**Семантика beanutils несимметрична для отображаемых свойств — воспроизводится как есть:** отображаемое свойство верхнего уровня (`prop(key)`) получает исходное значение параметра (массив строк) без конвертации; комбинация индексированного и отображаемого (`a.b[0](key)`) кладёт в существующий элемент-Map первый элемент параметра как строку; необъявленное свойство lazy-формы получает первый элемент параметра как строку. Всё это зафиксировано fixture-тестами.

### 2. JavaBean-путь: `BeanWrapper` + собственный парсер beanutils-выражений

Присвоение значений JavaBean-формам — через `BeanWrapperImpl` с `StrutsConversionService`. Синтаксис имён beanutils (`prop[0]`, `prop(key)`, `a.b`, комбинации) разбирается собственным резолвером (зеркало семантики `Resolver` beanutils: скобки `[i]`, круглые скобки `(key)`, точки) и транслируется в путь `BeanWrapper` (отображаемый ключ — в квотированной форме `prop['key']`, чтобы допускать любые символы в ключе).

**Альтернатива**: собственный рефлексивный сеттер — отклонено (дублирует `BeanWrapper`).

### 3. DynaBean-путь: метаданные `DynaClass` + тот же сервис

Формы, реализующие `DynaBean` (`DynaActionForm`, `DynaValidatorForm`, `LazyValidatorForm`, `BeanValidatorForm`), заполняются по метаданным `DynaClass`: тип из `DynaProperty` (включая компонент массива) конвертируется `StrutsConversionService`, присвоение — через `DynaBean.set(name[, index | key])`. Для необъявленных свойств lazy-форм значение присваивается как есть (семантика авто-добавления `LazyDynaBean`); неизвестные свойства прочих DynaBean — пропуск без ошибки (как `BeanUtils.populate`).

**Альтернатива**: оставить `BeanUtils.populate` для DynaBean — отклонено: конвертация идёт через статический `ConvertUtils`, то есть риск остаётся именно на динамических формах.

### 4. Сохранение контракта ошибок и порядка обработки

- Сбор параметров в `HashMap` и порядок до `BeanUtils.populate` не меняются (итерация записей — как сейчас).
- Присвоение идёт до первой ошибки; далее `ServletException("BeanUtils.populate", cause)` — сообщение сохранено для совместимости обработчиков/логов.
- Существующие проверки до populate не меняются: префикс `org.apache.struts.`, паттерн CVE-2014-0114, early-return при превышении multipart-лимита.
- `rationalizeMultipleFileProperty` переходит с `PropertyUtils.getPropertyType` на `BeanWrapper.getPropertyType` — populate-путь полностью без beanutils.

### 5. Размещение и жизненный цикл

Классы populate (`StrutsConversionService`, оркестратор присвоения) — в `org.apache.struts.util` рядом с `RequestUtils`; зависят только от `spring-core`. Сервис — неизменяемый синглтон populate-класса (набор конвертеров фиксирован на старте, потокобезопасность обеспечивается состоянностью конвертеров); публичные сигнатуры `RequestUtils.populate` не меняются, поэтому сервис не прокидывается параметрами.

### 6. Тестовая стратегия: fixture-матрица до замены

Сначала пишутся модульные тесты на текущем поведении (golden): набор кейсов из спеки `form-populate` — литералы Boolean, пустая строка, границы чисел, `Character`, `BigDecimal`, sql-даты/`Calendar`, `Class`/`File`/`URL`, `Enum`, отсутствие конвертера у `java.util.Date`, индексированные/отображаемые/вложенные имена, скаляр↔массив, неизвестные свойства, dyna-типы, lazy-авто-добавление. Тесты зелёные на текущей реализации → замена populate → те же тесты зелёные без правок. Поверх — существующие IT приложений (`./mvnw verify`) без изменений.

## Risks / Trade-offs

- [Семантика beanutils несимметрична (mapped верхнего уровня — сырой `String[]`, nested-indexed-mapped — строка первого элемента, нулевые значения вместо ошибок для примитивов)] → вся матрица (включая несимметрии) зафиксирована fixture-тестами ДО замены; любое расхождение — красный тест, а не продакшн-сюрприз.
- [`BeanWrapper` не понимает `prop(key)` и конвертирует значения Map, где beanutils кладёт сырой массив] → парсер выражений + собственные правила присвоения для mapped-веток (см. решение 2); fixture-тесты на комбинации.
- [`BeanValidatorForm` — DynaBean-фасад с собственными тонкостями] → покрывается fixture-тестом в core IT; при расхождении правится путь метаданных, не API.
- [Приложения, регистрировавшие кастомные конвертеры в статическом `ConvertUtils`, потеряют их действие в populate] → задокументировать в README (раздел «Совместимость»): populate движка не читает статический реестр; вопрос точки расширения — отдельным изменением при необходимости.
- [HashMap-порядок записей делает точку первой ошибки неочевидной] → сохраняем текущий сбор параметров в `HashMap` без изменений, порядок идентичен сегодняшнему.

## Migration Plan

1. Написать fixture-тесты текущего populate (зелёные на beanutils-реализации).
2. Внедрить `StrutsConversionService` + новый populate, переключить `RequestUtils` на них.
3. Fixture-тесты без правок — зелёные; `./mvnw verify` (все IT приложений) — зелёный.
4. Обновить README (раздел «Совместимость»): populate на Spring `ConversionService`, статический реестр не используется.
5. Откат — revert коммита; внешних артефактов и данных нет.

## Open Questions

- Поведение роста `List` при индексном присвоении за пределами размера не зафиксировано (fixture-тестов на этот случай нет; встречается редко). Выясняется при обнаружении в IT приложений; на подход не влияет.
