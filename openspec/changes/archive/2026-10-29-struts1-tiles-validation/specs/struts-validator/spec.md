# Spec Delta: struts-validator

## Purpose

Declarative form validation with commons-validator: rules are declared in `validation.xml` on top of `validator-rules.xml`, wired declaratively by `ValidatorPlugIn` through struts-config.xml, errors go into the standard Struts cycle (the input page, `html:errors`), and client scripts are generated by `html:javascript` — with the behavior of the weblegacy reference.

## ADDED Requirements

### Requirement: Wiring the validator as a plugin
`ValidatorPlugIn` SHALL be wired declaratively by a `<plug-in>` element of struts-config.xml with the init-parameters `pathnames` (a comma-separated list of resources: validator-rules.xml and validation.xml) and `stopOnFirstError`. The resources SHALL be loaded at startup; re-declaring the plugin in a module SHALL be a startup error.

#### Scenario: Declarative wiring
- **WHEN** struts-config.xml declares `ValidatorPlugIn` with `pathnames` pointing to validator-rules.xml and validation.xml
- **THEN** the validator is initialized at startup, and forms are validated by the rules without additional code

#### Scenario: A missing pathnames resource
- **WHEN** `pathnames` points to a non-existent resource
- **THEN** the application startup fails with the resource name

### Requirement: ValidatorForm validation by rules
A `ValidatorForm` form (and its subclasses) SHALL be validated by the validation.xml rules for its key name: the key is the form attribute from the configuration (`mapping.getAttribute()`); detected violations SHALL return `ActionErrors` with the rule messages, which the standard cycle directs to the input page; if there are no violations, the action is invoked.

#### Scenario: A required field is empty
- **WHEN** a field is declared `depends="required"` and submitted empty, and the mapping uses `validate="true"` with an input page
- **THEN** the action is not invoked, and the input page renders `html:errors` with the `errors.required` key message and the field label from `<arg>`

#### Scenario: Successful validation
- **WHEN** all form fields satisfy the rules
- **THEN** validate returns without errors and the action is invoked

### Requirement: The FieldChecks rule set
The rule set of the reference's `validator-rules.xml` SHALL work out of the box: required, requiredif, mask, minlength, maxlength, byte/short/integer/long/float/double (including the *Locale variants), date, intRange/longRange/floatRange/doubleRange, creditCard, email, url, validwhen. Messages SHALL be taken by the rule keys (`errors.required`, `errors.invalid`, `errors.range`, etc.) from message-resources, arguments — from the field's `<arg>` (positions 0–3, support for literals and `${var:...}`).

#### Scenario: The mask rule
- **WHEN** a field is declared `depends="required,mask"` with `var-name="mask"`, and the value does not match the regular expression
- **THEN** the input page shows the `errors.invalid` key message with the configured `<msg>`/`<arg>` (including the bundle from the `bundle` attribute)

#### Scenario: The range rule
- **WHEN** a field is declared `depends="intRange"` with min/max variables, and the value is out of range
- **THEN** the `errors.range` message is shown with min/max substituted from `<arg>` with `${var:min}`/`${var:max}`

#### Scenario: The validwhen rule
- **WHEN** a field is declared `depends="validwhen"` with a condition expression (`<var-name>test</var-name>`), and the condition is violated
- **THEN** the field is marked with the `errors.required` error

### Requirement: Multi-page validation with page
Fields of validation.xml with the `page` attribute SHALL be validated against the form's `page` value: fields whose page is not greater than the current one are validated; if the mapping does not declare a page limit, all fields are validated. `ValidatorActionForm`/`DynaValidatorActionForm` forms SHALL use the mapping path as the validation key (`mapping.getPath()`).

#### Scenario: The second page of a multi-page form
- **WHEN** a multi-page form submits `page=2`, and the mapping limits the allowed pages
- **THEN** only the fields with page ≤ 2 are validated; page 3 fields are not validated

#### Scenario: The key by action
- **WHEN** the mapping uses a form of type `ValidatorActionForm`, and validation.xml declares the rules by the action path name
- **THEN** validation is performed by the rules of that action

### Requirement: DynaValidatorForm validation
`DynaValidatorForm` (a dynamic form extending `DynaActionForm`) SHALL be validated by the validation.xml rules just like a static `ValidatorForm`, without a Java form class; the properties come from `<form-property>`, and the validation key is the form attribute from the configuration.

#### Scenario: A dynamic form by the rules
- **WHEN** struts-config.xml declares a form-bean of type `DynaValidatorForm`, validation.xml contains rules for its name, and the request submits invalid values
- **THEN** the input page shows the rule errors, and the action is not invoked

#### Scenario: form-bean inheritance with validation
- **WHEN** a form-bean descendant (`extends`) extends the base `DynaValidatorForm` with additional properties, and validation.xml declares rules by the descendant's name
- **THEN** both the inherited and the own properties are validated

### Requirement: Custom validators
Custom rules SHALL be wired by the `<global><validator>` section of validation.xml: the rule name, class and method, message key; such rules SHALL apply in `depends` on a par with the built-in ones.

#### Scenario: A custom rule
- **WHEN** validation.xml declares a global `twofields` validator with a custom class, and a field declares `depends="twofields"`
- **THEN** the custom class's method is invoked, and on violation its key's message is shown

### Requirement: html:javascript client scripts
The `html:javascript` tag SHALL generate commons-validator client scripts from the validation.xml rules: the static/dynamic mode, the form by `formName` (or the context form attribute), field methods by their rules; the output matches the reference (the form validation functions, `required` fields, the rules' JS utilities).

#### Scenario: Generating a form script
- **WHEN** a JSP contains `<html:javascript formName="registrationForm"/>`, and validation.xml declares the rules of that form
- **THEN** the page contains a JavaScript form validation function with the checks of the declared rules

#### Scenario: StaticJavascript
- **WHEN** a JSP requests the validator's static JS utilities (like mailreader's StaticJavascript.jsp)
- **THEN** the commons-validator utilities script is served without binding to a specific form
