# Proposal

## Why

Phases 1–3 delivered the engine, the tag libraries, and the Spring-native bean model, but three major Struts 1 subsystems are still missing: Tiles, multipart upload, and commons-validator. Without them the target weblegacy applications do not start — the upload/validator sections in `apps/examples`, `apps/cookbook`, and `apps/mailreader`: their configurations are already migrated into the repository but reference non-existent classes (`ValidatorPlugIn`, `UploadForm`, `RegistrationForm`), and `html:javascript` is declared in the TLD without an implementation. This is the next stage of the roadmap ("Tiles, upload, validation").

## What Changes

- **New module `spring-struts1-tiles`** — a Tiles 1.x-compatible implementation (resolves the roadmap's open question: a port of the weblegacy `struts-tiles` module, not tiles2): `TilesPlugin`, a definitions factory with XML parsing of `tiles-defs.xml` (digester rules, local DTDs 1.1/1.3/1.4, the default `I18nFactorySet` factory with localized file variants), `ComponentContext`/`ComponentDefinition`, tile controllers (`Controller`, `UrlController`, `ActionController`, `TilesAction`); the `struts-tiles` tag library (URI `http://struts.apache.org/tags-tiles`, 11 tags: insert, definition, put, putList, add, get, getAsString, useAttribute, importAttribute, initComponentDefinitions) on the Spring tag base; forward-to-tiles-definition resolution via a hook in the engine (a Spring-native analog of `TilesRequestProcessor`/`TilesPreProcessor` without replacing the processor). The definitions factory and tile logic services are registered as Spring components while classic access through `TilesUtil`/context attributes is preserved.
- **Multipart upload in the core**: the `org.apache.struts.upload` contract (`FormFile`, `MultipartRequestHandler`, `MultipartRequestWrapper`, limit-exceeded semantics via the request attribute `ATTRIBUTE_MAX_LENGTH_EXCEEDED`), a `CommonsMultipartRequestHandler` implementation on top of commons-fileupload2-jakarta (as in weblegacy), integration into the engine's populate step (`processMultipart` → handler → text/file elements → populate), multi-file semantics of `getFileElements() → FormFile[]` with rationalization to the form property type; limits from `<controller>`: `maxFileSize`, `maxSize`, `maxStringLen`, `fileCountMax`, `memFileSize`, `tempDir`, `bufferSize` (default values as in weblegacy, including `maxStringLen=4K`). If the request has already been parsed by the user's Spring multipart parser (`MultipartHttpServletRequest`), its parts are adapted into the same contract.
- **commons-validator in the core**: a port of the `org.apache.struts.validator` package — `ValidatorPlugIn` (init-params `pathnames`, `stopOnFirstError`; wired declaratively via `<plug-in>`), `Resources` (initValidator, arguments, bundles), `ValidatorForm`/`DynaValidatorForm` (the validation key is `mapping.getAttribute()`, `page` support), `FieldChecks` (the full rule set), `validwhen` on ANTLR4-runtime (as in weblegacy); `ValidatorActionForm`/`DynaValidatorActionForm` — in extras (as in weblegacy); engine resources: `validator-rules.xml`, `LocalStrings.properties`, the commons-validator JS utilities.
- **`html:javascript` implemented** (client-side generation of validation scripts in `spring-struts1-taglib`): the deferred tag from the `html-taglib` spec becomes functional.
- **Porting the target applications**: `examples` — enabling the `upload` and `validator` modules in web.xml and porting their classes/JSPs (`UploadForm`, `UploadAction`, `RegistrationForm`, etc.); a new `cookbook` war (`DynaValidatorForm` validation, a custom validator, the remaining sections); a new `mailreader` war (`DynaValidatorForm` with form-bean inheritance, the `ModuleConfigVerifier`, `MemoryDatabasePlugIn`, `DigestingPlugIn` plugins); the mailreader dao module is moved from the reference into the repository as its own module (resolves the roadmap's open question about mailreader-dao dependencies).
- **Configuration**: `ControllerConfig` gains `maxSize` and `fileCountMax` (as in weblegacy); the Tiles and validation plugins continue to be wired only declaratively via struts-config.xml.
- **New dependencies**: `commons-validator` 1.10.1, `antlr4-runtime` 4.13.2 (for validwhen), `commons-fileupload2-core` + `commons-fileupload2-jakarta` (as in weblegacy — 2.0.0-M1, possibly a newer stable 2.x).

## Capabilities

### New Capabilities

- `multipart-upload`: the `org.apache.struts.upload` contract (FormFile, MultipartRequestHandler) and its handling in the request lifecycle — parsing a multipart request, populating file and text elements, limit-exceeded semantics, `<controller>` settings.
- `struts-validator`: declarative commons-validator validation — `ValidatorPlugIn`, validator forms (ValidatorForm/DynaValidatorForm and the action variants), rules from validation.xml/validator-rules.xml, error messages, client-side `html:javascript`.
- `struts-tiles`: Tiles definitions and plugin — parsing tiles-defs.xml, the definitions factory (including i18n variants), tile controllers, forward-to-definition resolution, the struts-tiles tag library.

### Modified Capabilities

- `request-processing`: the populate step gains a multipart branch — a multipart request is parsed by the handler before populate, text and file elements fill the form, limit excess is detected via a request attribute; the forward-processing step gains tiles-definition resolution.
- `html-taglib`: the "Deferred validator tag" requirement is replaced by an implementation — `html:javascript` generates commons-validator client scripts from validation.xml.

## Impact

- **Code:** `spring-struts1-core` — the new packages `org.apache.struts.upload`, `org.apache.struts.validator` (+ `validwhen`), `org.apache.struts.extras.validator` and `org.apache.struts.extras.plugins`; changes to `StrutsHandlerAdapter` (the multipart populate branch, tiles-definition resolution in forwards), `RequestUtils` (populate over multipart elements), `Globals.MULTIPART_KEY`, `ActionForm` (access to the multipart handler), `ControllerConfig` (maxSize, fileCountMax); `spring-struts1-taglib` — `JavascriptValidatorTag`; the new `spring-struts1-tiles` module; `spring-struts1-apps` — examples (enabling the modules, new classes and JSPs), the new `cookbook` and `mailreader` wars, the new `mailreader-dao` module.
- **API:** the classic public Struts 1 API is preserved and extended with ports of the reference packages (`org.apache.struts.upload`, `org.apache.struts.validator`, `org.apache.struts.tiles.*`; the URI and TLD of `struts-tiles` are identical to weblegacy). No explicit BREAKING; the default value of `ControllerConfig.maxStringLen` is aligned with the reference (4K instead of the current 4M) — the deviation from weblegacy is removed before anyone relies on it.
- **Dependencies:** `commons-validator` 1.10.1, `antlr4-runtime` 4.13.2, `commons-fileupload2-core`/`commons-fileupload2-jakarta` (base version as in weblegacy — 2.0.0-M1) — the compile scope of the core; the tiles module reuses digester from the core.
- **Tests:** the `examples` ITs are extended with upload scenarios (a multipart POST, limit excess, multi-file) and validator scenarios (required/mask/minlength, validwhen, multi-page, javascript); the new IT suites `CookbookAppTest` and `MailreaderAppTest`; regression of the existing `blank`/`examples` ITs with unchanged expectations (blank additionally gets a real `ValidatorPlugIn` instead of the `TestPlugin` stub).
- **Out of scope:** the tiles2 bridge (`org.apache.tiles`), struts-el, BeanValidatorForm/LazyValidatorForm, faces/scripting apps, the Boot starter (phase 4), artifact publishing.
